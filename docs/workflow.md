# Правила работы с ветками и коммитами

## Ветка main
Ветка `main` является основной. Прямые коммиты в `main` запрещены. Любое изменение выполняется в отдельной ветке и попадает в `main` через Pull Request.

## Именование веток
Формат имени ветки: `type/short-topic`

- `feature/` — новая функциональность
- `fix/` — исправление ошибки
- `docs/` — документация
- `chore/` — служебные задачи
- `test/` — тесты

Примеры: `docs/workflow-rules`, `feature/add-parser`, `fix/date-format`

## Правила коммитов
Один коммит фиксирует одну законченную мысль. Сообщение коммита задаётся в формате: `<type>: <действие>`

### Типы коммитов:
- `feat:` — новая функциональность
- `fix:` — исправление ошибки
- `docs:` — документация
- `chore:` — служебные задачи
- `test:` — тесты
- `refactor:` — рефакторинг кода

### Примеры:
- `docs: add workflow rules`
- `feat: add app entrypoint`
- `chore: add gitignore`

## Правила Pull Request
В описании Pull Request обязательно указывать:
- цель изменения
- что сделано
- как проверить

Pull Request должен проходить локальные проверки:
```bash
ruff check .
python src/app.py

## Если добавлены тесты, они должны запускаться командой:
pytest

## Связь с Issue
## В описании Pull Request добавляется строка Closes #<номер> для автоматического закрытия Issue после вливания.

## Ответ на вопрос
Коммит «всё сразу» ухудшает сопровождение, потому что невозможно понять, 
какое изменение к чему относится, и при необходимости откатить одну правку 
приходится откатывать всё сразу.

Pull Request снижает риск регрессии, потому что изменения проходят проверку 
перед вливанием в основную ветку, и видно, какие именно файлы меняются.
